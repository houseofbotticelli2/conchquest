### Security

- [ ] #103 Do a restore drill -- actually restore a backup and bring the app up against it. Every backup is verified as *readable and complete* (the dumps are checked for `shell_finds` / `TABLE DATA auth users` before they count as a success, and the photo and account exports are row-counted), which rules out the common silent failures. But **nothing has ever been restored**, so the restore path itself is untested: a backup is a hypothesis until you've restored from it. Roughly an afternoon: (1) `createdb` a scratch local Postgres 17 database with PostGIS, (2) `pg_restore` the newest dump from `~/Library/Mobile Documents/com~apple~CloudDocs/Conchquest Backups/` into it, (3) point a local `npm run dev` at it via `DATABASE_URL`, (4) log in and confirm finds, beaches, and species are all there. Things that would plausibly bite and are worth finding out now rather than during an incident: whether the PostGIS extension and its types restore cleanly into a fresh database, whether `--no-owner` leaves anything unusable, and whether photo URLs still resolve (the bucket is separate from the dump, so a restored find can point at an object that only exists in the `photos/` backup). Also worth timing the whole thing -- "how long until we're back" is the number you'd actually want during a real outage. Write the result up as a short runbook so the next restore is a checklist, not a re-derivation.

- [ ] #106 Sync the NOAA/NDBC station lists from a scheduled job instead of from user requests. `node-cron` is already set up in `api/src/server.ts` (beach alerts every 30 min, cache cleanup Sundays 3am), so this is a third entry -- weekly, off-peak, calling the existing `ensureTideStationsSynced`/`ensureBuoyStationsSynced`. The point is structural, not performance: right now the *first* request after the refresh interval pays for the sync inline. Tonight's fixes (2026-08-18 -- `max(synced_at)`, single-flight + advisory lock, one bulk upsert) make that ~1-2s rather than 43s and stop it stampeding, but a user request should never be doing housekeeping at all. Moving it to cron means a slow or failing NOAA can't affect anyone's Shellcast screen, only a log line. **Keep a bootstrap path**: the request-side check should still fire when the table is genuinely *empty* (fresh deploy, new environment, a wiped database) -- just not when it is merely stale. That is the clean split: cron owns freshness, the request path owns "we have nothing at all". Once that holds, `NOAA_STATION_REFRESH_DAYS` stops being a request-path threshold and becomes just the cron schedule, so the env var can go. Pairs naturally with #105: the same job is the obvious place to retest excluded stations and put recovered ones back in rotation.
